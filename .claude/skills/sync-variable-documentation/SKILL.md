# Sync Variable Documentation

Используй этот скилл, когда нужно обновить существующую таблицу документации из локальной коллекции Variables, сохранив её текущую структуру и стилистику.

## Входные данные

- Выбранный frame таблицы документации.
- Название коллекции Variables.
- Режим, на основе которого показываются значения и alias-цели.
- Платформа Code Syntax. Если пользователь не уточнил платформу, используй только `WEB`.

## Порядок работы

1. Сначала внимательно изучи thumbnail выбранного frame.
2. Прочитай дерево выбранного frame и его ближайшего документационного родителя. Зафиксируй размеры, Auto Layout, колонки, строки, заливки, обводки, типографику и шаблоны header, group, data и row.
3. Найди локальную коллекцию по точному имени и выбранный mode. Получи все Variables этой коллекции без изменения их порядка.
4. Не изменяй сами Variables, их names, values, aliases или Code Syntax. Обновляй только документацию.
5. Сохраняй исходную стилистику: клонируй существующие header, group, data и row templates. Не создавай новый визуальный язык и не меняй размеры колонок, цвета, радиусы, шрифты или плотность без необходимости.

## Управление временными шаблонами

- Помни: `node.clone()` создаёт реальный SceneNode в документе, а не временный объект в памяти.
- Никогда не вызывай `clone()` только для сохранения переиспользуемого шаблона без немедленного размещения или последующего удаления этой копии.
- По возможности используй исходные существующие узлы как template sources до завершения генерации. Не удаляй их и их родителей, пока не созданы все необходимые финальные копии.
- Каждый созданный clone сразу добавляй в его окончательный intended parent внутри целевой таблицы.
- Веди список всех созданных узлов и отдельно список временных узлов.
- Если необходим staging-контейнер, создавай его внутри целевого frame, дай имя `_TEMP_VARIABLE_DOCS`, а после завершения обязательно удали целиком.
- Очистку временных узлов выполняй в `finally`, чтобы они удалялись и при частичном выполнении логики.
- Перед изменением сохрани IDs верхнеуровневых детей текущей страницы. После изменения сравни список: при редактировании существующей таблицы не должно появляться новых page-level слоёв.
- Любой новый узел, который не является потомком целевой таблицы или явно разрешённого документационного родителя, считается orphan и должен быть удалён.
- Не клонируй template, затем не удаляй его parent, продолжая клонировать из уже удалённого узла: такие копии могут оказаться на уровне страницы.

## Имена слоёв

> Для таблиц на DocTable этот раздел не применяется. Там действует раздел «Сохранность имён и связей» ниже. Правило ниже — только для старых, ещё не перенесённых таблиц из обычных frames.

- Внутри целевой таблицы имена сохраняются только у TEXT-слоёв и у компонентов иконок.
- Не изменяй имена TEXT-слоёв: они должны продолжать отражать текстовое содержимое макета.
- Компоненты иконок, их INSTANCE-слои и все descendants внутри этих instances исключены из правила очистки имён.
- Определяй иконку по имени main component или component: имя содержит `icon` без учёта регистра.
- Имя icon INSTANCE должно совпадать с именем его main component.
- Имена descendants внутри icon INSTANCE должны совпадать с соответствующими слоями main component. Если они ранее были очищены, восстанови их рекурсивно по структуре main component.
- Для самой таблицы и остальных нетекстовых descendants — FRAME, RECTANGLE, VECTOR, BOOLEAN_OPERATION, LINE и других SceneNode, которые не принадлежат icon component instance — установи имя в один пробел: `name = ' '`.
- Не используй пустую строку: Figma может автоматически вернуть стандартное имя типа `Frame` или `Rectangle`.
- Выполняй очистку имён после создания, клонирования и размещения всех финальных узлов, чтобы новые clones также получили корректные имена.
- Это правило действует только внутри целевой таблицы; не переименовывай её документационного родителя или другие слои страницы без отдельного запроса.

## Группировка

- Заголовок группы — полный путь группы из Variables **вместе с корневым namespace**: все сегменты пути, кроме последнего leaf. Корень не убирать.
- Разделяй вложенные сегменты через ` / `.
- Примеры:
  - `color/solid/500` → группа `color / solid`, строка `500`.
  - `color/alpha/black/24` → группа `color / alpha / black`, строка `24`.
  - `color/inverse/solid/450` → группа `color / inverse / solid`, строка `450`.
  - `typography/font-weight/thin` → группа `typography / font-weight`, строка `thin`.
  - Прямые leaf-токены под корнем (`color/contrast`) — в группе с именем корня: группа `color`, строка `contrast`.
  - Токен без группы (`icon-style`) — заголовок группы и имя строки совпадают: `icon-style`.
- Имя строки — последний сегмент имени переменной, без префиксов группы (`min`, а не `spacing-min`).
- Порядок групп определяется первым появлением группы в Variables.
- Порядок строк внутри группы должен совпадать с порядком Variables.
- Каждый Variable должен попасть ровно в одну группу; ничего не пропускай и не дублируй.

## Заголовки групп

- Каждый сегмент пути и каждый `/` — отдельный слой (в DocTable — отдельный экземпляр `Path Segment`):
  - `color` — отдельный сегмент;
  - `/` — отдельный сегмент;
  - `informative` — отдельный сегмент.
- Цвет: все сегменты и все `/` приглушённые (`surface/base/content/muted`), последний сегмент сильный (`surface/base/content/strong`). Если сегмент один, он сильный.
- Не объединяй составной заголовок в один текстовый слой.
- Для группы без подгруппы оставляй один сегмент и удаляй лишние `/` и пустые сегменты.

## Колонки

- `Name`: leaf-имя относительно группы.
- Колонки mode: по колонке на каждую моду коллекции (см. «Все modes»). В ячейке — прямой alias target или literal value этой моды.
- `Code syntax`: заголовок колонки всегда пишется именно так: `Code syntax`. Значение — точное `variable.codeSyntax` отображаемой платформы.
- Платформы: во всех таблицах только Web. Исключение — Primitives · Color: там Web, Android и iOS (см. «Code Syntax: сохранить формат таблицы»).
- Если syntax отсутствует, показывай `—`; не придумывай значение.
- `Description`: последняя колонка.

## Description

- Description должен быть общим для всей группы, а не повторяться в каждой строке.
- Используй один текстовый слой в Description-колонке, растянутой на высоту data-блока группы.
- Кегль всегда 12/16 (стиль `Caption/L/Medium`). Вариантов 14/18 больше нет.
- Составляй общий текст только на основе descriptions Variables этой группы. Не добавляй новый предметный смысл.
- Удали из общего Description конкретные числовые шаги, проценты и значения: например `50`, `500`, `alpha-24`, `24%`.
- После удаления чисел отредактируй грамматику, чтобы описание читалось естественно, но не меняй смысл.
- Общий Description должен объяснять назначение всей группы, а не отдельного шага.
- Проверь, что в итоговом общем Description не осталось цифровых символов.
- Высота data-блока должна быть не меньше высоты строк и не меньше высоты Description с внутренними отступами.

## Цветовые ячейки

- Каждый swatch обязательно привязывай к соответствующему Variable из документируемой коллекции, а не к его primitive alias target.
- Mode закрепляй **на самом swatch** (`setExplicitVariableModeForCollection` на экземпляре Swatch) — по mode его колонки. Не закрепляй mode на колонке, ячейке или таблице: ячейки и чипы окрашены переменными темы оформления, и закрепление на них перекрасит оформление (особенно на странице Themes).
- Для fallback/base paint используй реально resolved RGBA этого mode (включая alpha), никогда не используй серый placeholder. Получай его через `variable.resolveForConsumer(swatch)` уже после закрепления mode.
- Текст в mode-колонке показывает прямой alias target, а fill swatch связан с Variable документируемой коллекции.
- Явный mode override на корне таблицы относится к коллекции оформления документации — его не трогай.

## Проверка

Перед завершением обязательно проверь:

1. Количество строк равно количеству Variables коллекции.
2. Все Variables покрыты один раз.
3. Code Syntax взят из `variable.codeSyntax` каждой отображаемой платформы.
4. Каждый swatch имеет bound color Variable из той же коллекции.
5. Каждый swatch в mode-колонке рисуется в mode своей колонки: `swatch.resolvedVariableModes[collection.id]` равен mode колонки.
6. На таблице, колонках и ячейках нет explicit mode override документируемой коллекции — только на swatches.
7. Fallback paint каждого swatch равен resolved RGBA его mode.
8. Для каждой группы существует ровно один общий Description без числовых значений.
9. Составные заголовки групп сохраняют отдельные сегменты и `/`.
10. Текст не обрезан, строки выровнены, Description помещается, таблица и родительский frame имеют достаточную высоту.
11. Все созданные финальные узлы являются потомками целевой таблицы или разрешённого документационного родителя.
12. На уровне страницы не осталось новых template clones, `_TEMP_VARIABLE_DOCS` или других orphan-слоёв.
13. Имена: в DocTable — ни одного переопределения имени у экземпляров; в старых таблицах — правило раздела «Имена слоёв».
14. Каждый icon INSTANCE совпадает по имени с main component, а его descendants — с соответствующими слоями component definition.
15. Сделай screenshot итогового frame и визуально проверь результат.

Если обнаружено несоответствие в исходных Variables — например, name `solid/600`, а WEB syntax заканчивается на `solid-700` — не исправляй Variable без отдельного запроса. Сохрани точные исходные данные и сообщи пользователю о расхождении.

## Согласованные правила синхронизации — приоритетные уточнения

Этот раздел имеет приоритет над противоречащими ему прежними правилами входных данных, выбора одного mode, ограничения только WEB, запрета любых цифр в Description и проверки количества строк одной таблицы по всей коллекции. Остальные защитные правила выше сохраняются.

### Область запуска и поиск

- С выделением обновляй выбранную таблицу по указанной пользователем локальной коллекции. Если выбрана строка или ячейка, найди ближайшую таблицу документации; не расширяй область на другие таблицы без запроса.
- Без выделения анализируй документацию на всех страницах текущего документа и обновляй только таблицы, в которых есть отличия от Variables. Явно заданную пользователем область считай ограничением.
- Сначала прочитай список страниц; загружай и анализируй их последовательно, по одной странице за вызов. Не используй loadAllPagesAsync.
- Для каждой таблицы установи связь с коллекцией и документируемым namespace по существующим bindings, именам групп, Name, mode headers и Code Syntax. Одного совпадения названия страницы недостаточно. Не полагайся на технические имена frames: они могут состоять из одного пробела.
- До изменений изучи предоставленный thumbnail; если его нет, получи изображение таблицы. Повторно читай актуальную структуру документа, не используй прошлый snapshot как текущее состояние.
- Если связь таблицы с коллекцией неоднозначна, уточни её у пользователя и не изменяй эту таблицу наугад. Сообщай о коллекциях без документации; создание новых страниц не входит в обычную синхронизацию.

### Источник истины, порядок и покрытие

- Источник истины — Variables. Не изменяй Variable names, values, modes, aliases, descriptions или Code Syntax.
- Используй порядок variableIds коллекции, без алфавитной сортировки, сортировки по числам или яркости. Группы идут по первому появлению в этом порядке; строки внутри группы повторяют порядок Variables.
- Сопоставляй существующие строки с Variable IDs по bindings там, где они доступны; иначе используй полное имя с namespace и другие однозначные признаки. Не сопоставляй только по leaf: он может повторяться в разных группах.
- Полный путь строки = заголовок группы (без пробелов вокруг `/`) + `/` + имя строки. Он обязан совпадать с именем переменной.
- Добавляй новые токены, удаляй строки удалённых токенов и пустые группы. Rename и перенос токенов между группами отражай в документации. Способ обновления — переиспользование строк либо перестроение — выбирай по надёжности результата; итоговая структура должна соответствовать Variables.
- В одной строке показывается один токен с данными всех modes. Каждый токен покрывается ровно один раз в соответствующем разделе; число mode-ячеек не считай числом токенов.
- Если коллекция распределена по нескольким таблицам, отдельную таблицу сверяй с её namespace, а суммарное покрытие всех таблиц — со всей коллекцией. Не добавляй в выбранную таблицу токены чужого раздела.
- Если на странице документирована не та коллекция (строки совпадают с другой коллекцией), это расхождение: сообщи и перестрой таблицу по правильной коллекции только по запросу.

### Все modes

- Показывай все modes коллекции в порядке collection.modes. Названия колонок должны точно совпадать с названиями modes. Отдельный выбранный mode больше не ограничивает набор колонок. Колонка `Value` — только у коллекций с одним mode.
- Создавай недостающие mode-колонки, удаляй колонки modes, которых больше нет, и отражай переименования. При добавлении колонок расширяй таблицу по формуле ширины (раздел «Геометрия DocTable»), не сжимая колонки.
- Для каждого mode показывай прямой alias target либо точное literal value. Разрешай alias-цепочки для отображения swatches с учётом mode-контекста соответствующей колонки, modes зависимых коллекций и циклических или недоступных alias.
- Каждый swatch связан с документируемым Variable; mode закрепляется на самом swatch (см. «Цветовые ячейки»). Не меняй тему оформления таблицы ради цвета колонки.

### Code Syntax: сохранить формат таблицы

- Заголовок колонки — `Code syntax` во всех таблицах.
- Формат по таблицам: везде только WEB, в Primitives · Color — WEB, ANDROID и iOS. Не унифицируй без отдельного запроса.
- Для каждой отображаемой платформы используй точный `variable.codeSyntax` этой платформы. Если значение отсутствует, показывай «—»; не генерируй синтаксис по имени и не исправляй исходные несоответствия.
- Primitives · Color — согласованный формат: один блок Code Syntax на группу, растянутый на её высоту, с шаблоном шага `00` (`var(--color-red-00)`, `red00`, `Color.red00`). Шаблон выводи из `codeSyntax` переменной **этой** группы: замени в нём номер шага на `00`. Не копируй блок из соседней группы. Если у переменных группы разные шаблоны, сообщи о расхождении.
- В группе из одного токена (например, `color/alpha/transparent`) показывай его точный syntax без шаблона.

### Description: обобщать по необходимости

- Если группа содержит несколько токенов, объединяй descriptions её Variables в одно групповое описание. Убирай повторы; допустимы минимальные грамматические изменения. Сохраняй общее назначение и существенные различия между токенами, не добавляй нового предметного смысла.
- Для одиночного токена сохраняй исходный description, не обобщая его без необходимости. Отсутствие описаний не заполняй придуманным назначением.
- В Variables повторяющиеся descriptions допустимы и не требуют исправления. Ограничение места относится к таблице, а не к исходным Variables.
- Убирай конкретные числовые шаги и проценты, когда они лишь повторяют строки шкалы. Не применяй механический запрет всех цифр: числа, существенные для смысла, единицы и важные ограничения сохраняй.
- Существующее общее описание можно сохранить, если оно соответствует текущим descriptions Variables; обновляй его, если состав или назначение группы изменились.

### Changelog и разделение таблиц

- Не добавляй и не редактируй Changelog, версии, задачи, автора, даты и записи истории. Changelog обслуживается отдельным скиллом. Заглушки (`Task-000`, `1.0.1`) оставляй как есть.
- Primitive Color сохраняй отдельными блоками по цветам, не объединяй всю коллекцию в одну таблицу. Сохраняй остальные существующие разделения коллекций по namespace и раскладку страниц (Primitives · Typography — один фрейм с пятью таблицами, Responsive — четыре фрейма).
- Для новых цветовых разделов в коллекции добавляй соответствующий блок по существующему шаблону только в однозначно установленной области документации. Не копируй историю чужого цвета как историю нового блока. Если подходящего контейнера или безопасного шаблона без выдуманной истории нет — уточни у пользователя.
- Создание нового документационного блока считается намеренным финальным результатом, а не orphan. При обычном обновлении существующей таблицы правило отсутствия новых page-level узлов остаётся обязательным; новые блоки допускаются только для новых разделов в определённой области и должны быть явно учтены.

### Геометрия, повторный запуск и итоговая проверка

- Сохраняй существующий визуальный язык, Auto Layout, component identities, переменные оформления, шаблоны заголовков, строк и описаний.
- Высоты соответствующих строк во всех колонках должны совпадать. Если Description выше списка строк, увеличь data-блок и согласованно растяни колонки; не оставляй их разной высоты и не обрезай текст.
- Переполнения длинного кода в ячейках высотой 44 известны и отложены: не обрезай код многоточием и не меняй высоту строк ради них без запроса.
- Скилл не является фоновым наблюдателем: синхронизация происходит только при запуске пользователем.
- Повторный запуск при отсутствии изменений не должен перестраивать, дублировать или перемещать актуальные таблицы. Сначала сравни данные и структуру, затем изменяй только то, что действительно требует обновления.
- Дополнительно к проверкам выше проверь порядок групп и строк, покрытие namespace и всей коллекции, все modes в исходном порядке, значения каждой mode-ячейки, все существующие платформы Code Syntax, согласованность высот и сохранность Changelog.
- После каждого обновления визуально проверь итоговую таблицу, затем убери временные узлы. Для обхода всего документа веди список обновлённых, актуальных и неоднозначных разделов; при сбое не заявляй о полном завершении.
- В завершении кратко сообщи, какие разделы обновлены, какие уже актуальны и где обнаружены неоднозначности, недоступные aliases или расхождения исходных данных. Если изменений нет, так и сообщи.

## Только таблица — приоритетное правило

Это уточнение имеет приоритет над любым прежним указанием копировать целый документационный блок или сохранять боковую информационную панель как часть результата синхронизации.

- При создании и обновлении работать только с таблицей токенов.
- Не создавать, не копировать и не восстанавливать боковую панель с логотипом, названием раздела и вводным описанием.
- Из образца брать только саму таблицу, а не весь блок вместе с информационной панелью или Changelog. Не переносить лишнюю панель даже временно, если можно скопировать только таблицу.
- Сохранять заголовки колонок, заголовки групп и Description внутри таблицы: они необходимы и не относятся к исключаемой вводной панели.
- Существующие информационные панели и Changelog вне таблицы не изменять без отдельного запроса. Сам по себе запуск синхронизации не разрешает их удаление.
- После удаления явно указанной пользователем панели не оставлять пустое место под неё: контейнер таблицы должен подстроиться под оставшееся содержимое без изменения данных и структуры таблицы.

## Нативная система DocTable — приоритетное дополнение

Это дополнение имеет приоритет над всеми противоречащими ему прежними указаниями клонировать обычные frames и текстовые слои, очищать технические имена слоёв и использовать временные или универсальные swatch-заглушки. Не переписывай и не отменяй остальные правила: источником данных остаются Variables, сохраняются порядок коллекции, все modes, точный Code Syntax, правила descriptions и исключение Changelog и боковых панелей. Синхронизация данных не даёт разрешения менять main components.

В других файлах сначала обнаруживай соответствующие локальные main components по именам и проверяй их назначение; не переноси IDs между файлами.

Перед использованием каждого ID проверь ожидаемое имя, тип `COMPONENT`/`COMPONENT_SET` и локальность (`remote === false`). При несовпадении не используй узел наугад.

### Иерархия, нативные slots и properties

- Используй linked native INSTANCE для каждой структурной части и каждой ячейки. Переменное количество групп, колонок, строк и сегментов обеспечивай содержимым настоящих узлов типа `SLOT`.
- Иерархия:

```
Table
├─ Header › Cells: Cell / Text × N         (Name | <modes или Value> | Code syntax | Description)
└─ Groups: Group × по группе переменных
   ├─ Heading › Group Heading › Segments: Path Segment × …
   └─ Body › Group Body › Columns:
        Column (Name) › Rows: Cell / Name × строки
        Column (<mode>) › Rows: Cell / Value | Cell / Text | Cell / Color Value × строки   — по колонке на mode
        Column (Code) › Rows: Cell / Text × строки     (Primitives · Color: один Code Syntax на группу)
        Cell / Description                              (одна на группу, прямо в Columns)
```

- Число колонок каждой Group Body равно числу ячеек заголовка.
- Значения в ячейках:
  - alias на цвет → `Cell / Value` › `Value[Leading=Swatch]`: `Label` = имя alias target, Swatch по правилам «Цветовые ячейки»;
  - alias на число или строку → `Value[Leading=Icon]` с `icon.16.number`, `Label` = имя alias target;
  - literal string или number → `Cell / Text`;
  - примитив цвета → `Cell / Color Value`: Solid — HEX; Alpha — HEX и прозрачность; слой `Color` внутри Swatch привязан к самой переменной.
- Текст экземпляров меняй через `instance.setProperties` с полными runtime property IDs, включая суффиксы `#...`; сначала прочитай реальные componentProperties. Не заменяй этот путь прямым изменением `characters`.
- Различающееся содержимое иконок помещай в `Icon` slot, используя исходные icon instances. Не подменяй slots механизмом `INSTANCE_SWAP`.
- Перед любым изменением прочитай существующее содержимое, в том числе вложенные `SLOT`, и сравни данные по Variable IDs. Меняй только соответствующие instance properties, разрешённые fill overrides и требуемое новое содержимое slots; не пересоздавай актуальные узлы без необходимости.

### Нейтральные masters и реальные данные только в instances

- Все main components остаются универсальными: нейтральные Labels (`token`, `collection/token`, `var(--token-name)`), нейтральные Description и нейтральный серый swatch без binding. Серый default swatch допустим ТОЛЬКО в master component, но не в живой документации. Примеры внутри masters Header и Group Body — 4 колонки по 400.
- Реальные имена токенов и коллекций, Code Syntax, descriptions, цвета и modes задавай только через properties экземпляров и содержимое их slots. Обычная синхронизация токенов никогда не обновляет definitions masters.
- Не делай detach instances. Не изменяй геометрические descendants под instances.
- Разрешён fill override с paint binding к документируемому Variable и explicit mode на самом Swatch. Base paint — точный resolved RGBA этого mode, включая alpha.
- Сохраняй переменные оформления темы и explicit mode коллекции оформления на корне таблицы.

### Сохранность имён и связей

- Полностью исключи все поддеревья COMPONENT и INSTANCE из очистки технических имён. Для DocTable не применяй `name = ' '`.
- **Никогда не присваивай `instance.name`** — даже значение, равное имени компонента. Это создаёт переопределение имени, и переименование слоя в master перестаёт доходить до экземпляра.
- Если переопределение имени уже есть: у экземпляра без слотов — сохрани свойства и прочие overrides, вызови `resetOverrides()`, верни всё, кроме имени. У экземпляра со слотами `resetOverrides()` запрещён (сотрёт содержимое слотов): создай новый экземпляр того же master, вставь на место старого, перенеси детей слотов через `appendChild`, удали старый. Иди от самого глубокого уровня к корню, по одному уровню вложенности за вызов: в рамках одного вызова перенесённые узлы отдают устаревшие id.
- Сохраняй семантические имена slots, имена masters и instances, ссылки main component и имена component properties в точности.

### Геометрия DocTable: hug / fill / fixed

Правило: **колонка = 400 px и FILL; таблица растягивается целиком; все ширины — целые числа.**

| Слой | Ш / В | Почему |
|---|---|---|
| Table (корень) | FIXED / HUG | Единственная заданная ширина: `W = N × 400 + (N − 1) + 8`, где 1 — зазор-разделитель, 8 — отступы 4 + 4. N = 4 → 1611, 5 → 2012, 6 → 2413, 7 → 2814, 9 → 3616 |
| Header, Group, Group Heading, Group Body, все slots | FILL / HUG | Растягиваются вместе с таблицей |
| Column | FILL / HUG | Колонки делят ширину поровну |
| Cell / Text в Header › Cells | FILL / FIXED 44 | Высота строки — токен `base/2xl` |
| Cell / Text, Name, Value, Color Value в Rows | FILL / FIXED 44 | То же |
| Cell / Description `Align=Top` | FILL / FILL | Группа из нескольких строк: тянется на высоту группы |
| Cell / Description `Align=Center` | FILL / FIXED 44 | Группа из одной строки |
| Code Syntax | FILL / FILL | Тянется на высоту группы. В группе из одной строки: HUG по высоте, а Column и ячейки Name/Value в ней FILL по высоте |
| Path Segment, Value, чипы кода, подписи платформ | HUG / HUG | По длине текста |
| Иконки, слоты иконок, Swatch | FIXED 16 × 16 | Размер иконки |

- **Особенность slots.** Внутри slot FILL-элемент с собственными горизонтальными отступами получает ширину содержимого плюс отступы, то есть на 24 px шире соседей. Поэтому у Cell / Description и Code Syntax горизонтальные отступы на корне равны 0, а 12 px (токен) стоят на внутренних фреймах: `Content` у описания, строки `Web / Android / iOS` у кода. Не возвращай отступы на корень и не ставь этим ячейкам FIXED по ширине.
- Смена варианта (`setProperties({ Align })`) сбрасывает FIXED-высоту — после неё заново выставь режимы по таблице выше.
- Размер экземпляра внутри slot через `resize` не переопределяется — восстанавливай его режимом FILL.
- Если родительский фрейм страницы FIXED по ширине и уже таблицы, переведи его в HUG.
- Конфигурируй корень нового instance до добавления в slot. После вставки проверь фактические sizing и геометрию.
- Перед изменением текста и любым действием, вызывающим text reflow, загрузи все требуемые шрифты.

### Стили и токены

- Тексты — только через текстовые стили: `Body/M/Medium` (14/18) в ячейках и сегментах, `Caption/L/Medium` (12/16) в описаниях. В экземплярах не задавай кегль, интерлиньяж, начертание и letter-spacing отдельными переменными или числами. Если стиль отвязался, верни стиль соответствующего текста master через `setTextStyleIdAsync`.
- При восстановлении overrides не переноси пустой `textStyleId` — это отвязывает стиль.
- Отступы и радиусы — токены (`spacing/base/4xs` = 4, `spacing/base/3xs` = 8, `base/2xs` = 12, `base/2xl` = 44). Числом допускается только зазор 1 px между колонками: это линия-разделитель.
- Заливки оформления: ячейки — `surface/base/fill/raised`, текст — `content/strong` / `content/muted`, таблица — `fill/page`.

### Разделять COMPONENT_MIGRATION и DATA_SYNC

- Явно различай и отдельно отражай в отчёте `COMPONENT_MIGRATION` и `DATA_SYNC`. Миграция на components сохраняет текущий контент в точности. Она сама по себе не означает сверку или обновление данных из Variables.
- Если текущие alias, mode или source-поля расходятся с Variables, не представляй сохранение такого контента при миграции как выполненный DATA_SYNC. Зафиксируй расхождения без изменения исходных Variables.
- При обычном запросе синхронизации обновляй данные экземпляров из Variables по правилам выше. Если сохранение текущего вида конфликтует с возможностями components, останови затронутый раздел, объясни конфликт и запроси согласование; никогда не меняй main молча.
- Набор компонентов поддерживает: составной literal color (HEX + opacity) — `Cell / Color Value`; групповой блок Web/Android/iOS — `Code Syntax`; описание группы из одной строки — `Align=Center`. Для других особенностей макета сначала проверь, есть ли подходящий согласованный компонент; при отсутствии сообщи проблему вместо упрощения или изменения masters.
- Работай только с таблицей. Существующие Changelog и боковые панели вне таблицы сохраняй без изменений.

### Безопасная замена и проверка

- Создавай временные новые корни и staging только внутри intended документационного контейнера. Не оставляй page-level orphan-узлы. До удаления исходной таблицы полностью подготовь replacement и проверь текст, геометрию, fills, modes и bindings. При неуспехе сохрани оригинал и убери только созданные этой операцией временные узлы.
- При переносе существующей таблицы делай структурное сравнение каждого TEXT (позиция, высота, текст, шрифт, заливка) и каждой заливки до и после. Старое удаляй только при чистом сравнении.
- Длинные записи делай порциями (одна таблица за вызов) и идемпотентно. Если связь оборвалась, сначала прочитай состояние холста: запись часто успевает пройти.
- Повторный запуск без изменений не должен перестраивать, перемещать или дублировать таблицу.
- Перед отчётом все проверки должны дать 0 нарушений:
  - каждая структурная часть и ячейка — связанный `INSTANCE` своего master; в slots нет frames и других не-экземпляров; скрытых слоёв и пустых slots нет;
  - колонки тела совпадают с ячейками заголовка по `x` и `width` (допуск 0.01); все колонки ровно 400; ширина таблицы по формуле;
  - строки против Variables: пропусков 0, лишних 0, дублей 0; показаны все modes;
  - Code Syntax совпадает с `codeSyntax` переменных на всех отображаемых платформах;
  - каждый swatch в mode-колонке привязан к документируемой коллекции и рисуется в mode своей колонки;
  - отвязанных текстовых стилей 0; переопределений имени 0;
  - screenshot итоговой таблицы проверен визуально — в том же вызове или сразу после.
- В финальном отчёте отдельно укажи выполненную миграцию и/или синхронизацию, обновлённые и уже актуальные разделы, пропущенные разделы и причины, неподдержанные форматы, расхождения исходных данных и оставшиеся issues. При блокировке или частичном результате не заявляй о полном завершении.
